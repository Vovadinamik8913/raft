# Raft

Учебная реализация алгоритма консенсуса **Raft** на Go по мотивам статьи
Diego Ongaro и John Ousterhout — *«In Search of an Understandable Consensus
Algorithm (Extended Version)»* (`docs/raft.pdf`).

Проект разбит на части по мере прохождения материала. Ниже описана текущая
реализация и план дальнейших этапов.

## Быстрый старт

Клонируйте репозиторий и подтяните зависимости:

```bash
go mod tidy
```

Запустите кластер из трёх узлов в **трёх разных терминалах**:

```bash
# Терминал 1
make run ARGS="--id=node1 --port=8001 \
  --peers=http://localhost:8002,http://localhost:8003"

# Терминал 2
make run ARGS="--id=node2 --port=8002 \
  --peers=http://localhost:8001,http://localhost:8003"

# Терминал 3
make run ARGS="--id=node3 --port=8003 \
  --peers=http://localhost:8001,http://localhost:8002"
```

> В `--peers` перечисляйте URL **других** узлов — без самого себя. Каждый URL должен соответствовать отдельному узлу с уникальным ID.
> Повторяющиеся URL удаляются; RPC к самому себе не дают дополнительного голоса.

Через 1–2 секунды (после истечения election timeout) один из узлов станет
лидером. Проверьте:

```bash
curl -s http://localhost:8001/status | jq
curl -s http://localhost:8002/status | jq
curl -s http://localhost:8003/status | jq
```

Ожидаемый вывод (пример):

```json
{"id":"node1","state":"LEADER","term":1,"leader_id":"node1"}
{"id":"node2","state":"FOLLOWER","term":1,"leader_id":"node1"}
{"id":"node3","state":"FOLLOWER","term":1,"leader_id":"node1"}
```

## Флаги командной строки

| Флаг          | По умолчанию | Описание                                     |
|---------------|--------------|----------------------------------------------|
| `--id`        | `node1`      | Уникальный ID узла в кластере                |
| `--port`      | `8000`       | HTTP-порт для REST API и RPC                 |
| `--peers`     | —            | Список URL пиров через запятую               |

## HTTP API

### Реализовано (Part 1)

| Метод | Путь              | Назначение                                    |
|-------|-------------------|-----------------------------------------------|
| POST  | `/request_vote`   | RPC `RequestVote` (§5.2 статьи)               |
| POST  | `/append_entries` | RPC `AppendEntries` — в Part 1 только heartbeat (§5.3) |
| GET   | `/status`         | Текущее состояние узла                        |

Пример `/status`:

```json
{
  "id": "node1",
  "state": "LEADER",
  "term": 3,
  "leader_id": "node1"
}
```

### Планируется

- `POST /add_entries` — добавление записи в лог (Part 2).
- `GET  /show_log` — просмотр лога (Part 2).
- `GET/PUT /kv/{key}` — key-value API (Part 3).
- `POST /cas` — compare-and-swap (Part 4).
- `POST /lock` / `DELETE /lock` — distributed lock (Part 4).

## Структура проекта

```
.
├── cmd/
│   └── raft-node/
│       └── main.go           # Точка входа: флаги, HTTP-сервер, graceful shutdown
├── docs/
│   └── raft.pdf              # Оригинальная статья
├── internal/
│   └── raft/
│       ├── handler/          # Тонкий HTTP-слой (JSON ↔ вызовы метода узла)
│       │   └── handler.go
│       ├── model/            # Типы данных и разделяемое состояние
│       │   ├── models.go     # DTO RPC, NodeStatus
│       │   └── state.go      # State (term, votedFor, role) + мьютекс
│       └── node/             # Логика узла Raft (выборы, heartbeat)
│           └── node.go
├── Makefile
├── README.md
└── go.mod
```

Пакеты разделены по слоям:

- **`model`** — «тупые» данные без логики. Переиспользуется и `handler`,
  и `node`.
- **`node`** — ядро алгоритма: переходы состояний, таймеры, RPC к пирам.
- **`handler`** — HTTP-обвязка. Знает только про JSON и `*node.RaftNode`.
- **`cmd/raft-node`** — склейка: парсинг флагов, `signal.NotifyContext`,
  `http.Server`.

Такое разделение позволит в Part 2–4 добавлять подпакеты (например,
`internal/raft/log`, `internal/kv`, `internal/lock`) без переписывания
существующих слоёв.

## Как это работает

Part 1 реализует выборы лидера по §5.2 статьи:

1. **Состояния.** Каждый узел находится в одном из трёх состояний —
   `FOLLOWER`, `CANDIDATE`, `LEADER`.
2. **Election timer.** У фолловера тикает таймер со случайной задержкой
   (`ElectionTimeoutMin..Max`, по умолчанию 500–1000 мс). Если таймер
   истекает — узел становится кандидатом.
3. **Голосование.** Кандидат увеличивает `currentTerm`, голосует за себя
   и параллельно рассылает `RequestVote` всем пирам. Узел голосует за
   кандидата, если:
   - `term` кандидата не меньше его собственного,
   - он ещё не голосовал в этом терме (или голосовал за этого же кандидата),
   - лог кандидата не менее актуален (в Part 1 лог пуст — проверка
     тривиальна).
4. **Победа.** Набрав голоса строгого большинства `(N/2 + 1)`, кандидат
   становится лидером и запускает цикл heartbeat'ов.
5. **Heartbeat.** Лидер каждые `HeartbeatInterval` (100 мс по умолчанию)
   рассылает пустые `AppendEntries`. Получив такой RPC, фолловер сбрасывает
   таймер и остаётся фолловером.
6. **Обнаружение устаревшего лидера.** Если узел видит `term` больше
   своего — он немедленно становится фолловером и сбрасывает таймер.

Part 1 хранит `currentTerm` и `votedFor` только в памяти: при рестарте они
сбрасываются. Сохранение на диск отложено; без него не обеспечивается гарантия
безопасности выборов при потере состояния из-за перезапуска.

Выборы повторяются по случайному таймауту, если большинство не набрано.
Голоса учитываются по мере получения и только для текущих выборов.
У лидера таймер выборов отключён; heartbeat отправляется сразу после победы.
Ctrl+C останавливает таймеры, отменяет исходящие RPC и завершает HTTP-сервер.

REST API использует Gin. `/append_entries` принимает только пустые heartbeat:
`entries: []`, `null` или отсутствие поля. Непустые `entries` возвращают HTTP 400.
Ссылка на отсутствующую запись (`prev_log_index` / `prev_log_term`) возвращает
`success: false`. Некорректный JSON, пустые ID и отрицательные поля возвращают 400.
CLI принимает только `--id`, `--port`, `--peers`.

Подробности — в Figure 2 и §5.1–5.2 статьи (`docs/raft.pdf`).

## Ручные проверки

### 1. Кто лидер?

```bash
for p in 8001 8002 8003; do
  echo -n "port $p: "
  curl -s http://localhost:$p/status | jq -c '{state,term,leader_id}'
done
```

### 2. Перевыборы после падения лидера

Убейте процесс лидера (Ctrl+C в его терминале), подождите ~1–2 секунды и
снова выполните команду выше. Один из оставшихся узлов станет `LEADER` с
**увеличенным `term`**.

### 3. Отказ одного из трёх

Кластер из трёх узлов выдерживает падение одного. Если упадут два — лидера
выбрать не получится (нет кворума), и `/status` будет показывать `CANDIDATE`
с растущим `term`. Изолированный старый лидер может оставаться `LEADER`, пока
не узнает о большем term: базовый Raft не требует step-down при потере кворума.

### 4. Split vote

Если запустить все три узла одновременно, возможен split vote — никто не
наберёт большинство в первом терме. Raft разрешает это сам: кандидаты
получают случайные таймауты, и в следующем терме побеждает один из них.
